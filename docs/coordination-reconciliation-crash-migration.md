The two-process accounting tests do **not** claim that two simultaneously valid process-local lease handles exist. Handles cannot be serialized across processes. The normal owner either commits before releasing its valid lease, or releases first and is fenced while the new owner performs approved reconciliation. This exercises the actual fencing contract and both accounting-authority orders.

## Invocation accounting and Hold-release checks

`coordination-reconciliation-process.test.ts` additionally contains these real-DB tests (no process-kill substitution is implied):

- `US-16: late verified Usage updates original Invocation accounting without returning its consumed Model debit or changing its stopped record`: a synthetic model response is lost, leaving the Invocation `REVIEW_REQUIRED`. A fresh administrative Generation verifies and approves complete usage. The original Invocation, model ledger, journal, and one consumed Model debit remain byte-for-byte unchanged. The authenticated Invocation Reader reports committed input/output `2/3`, outstanding `0/0`, and the same `modelCalls=1`. Complete `NOT_APPLICABLE_VERIFIED` response evidence permits a separately approved Hold-release Plan as the normal control; reconciliation itself never releases the Hold.
- `IN-04: Hold Release cannot bypass {PARTIAL_USAGE,RESPONSE_UNAVAILABLE,DISPUTED}; refusal preserves Grant, Invocation, accounting, workflow and callbacks`: three quiescent Invocation cases independently refuse Hold-release Plan creation. Full durable-table, workflow-snapshot, and callback-counter comparisons establish no preceding effect. No ACTIVE/DRAINING Invocation masks the obligation under test.

The initial assertions for these new fixtures assumed a finished status and an already materialized Hold. Inspection established the actual existing contract: a lost response stops at `REVIEW_REQUIRED`, and acquiring a fresh administrative Generation materializes the Hold. The tests now create that authorized state explicitly; production guards were not relaxed.

The separate `coordination-reconciliation-expiry.test.ts` adds two real-time, real-DB checks; these are not additional SIGKILL scenarios. `IN-08` waits beyond a committed Verification's expiry without changing Generation or trust, while its Plan/Grant deadlines remain valid. Authenticated receipt reads, effective accounting and every durable row remain unchanged. `US-12` returns the original bounded response after its persisted collection deadline, observes `CONTINUATION_EXPIRED`, and proves that ordinary settlement is refused before any write. A new Generation and separate authenticated 4C approval then settle Usage while preserving the original Invocation, deadline, consumed debit, Ledger, Journal, steps and artifacts. Its missing response still requires review and its Hold remains HELD.

## Counters and resources

All ordinary reconciliation and restart fixtures count original Action/Model calls separately from synthetic signature verification. They perform zero original business Action/Model calls. Receipt-only restart performs zero verifier calls as well. ACTIVE/DRAINING and late-Invocation fixtures start one pre-existing synthetic bounded planning call to create a real consumed debit and an in-flight model attempt; reconciliation never starts a second call. The active dispute test also verifies zero action, PLAN, and VERIFY executor calls. Ed25519 keys are generated for each temporary fixture; the process harness writes them only into its private temporary directory so sibling processes can use the same synthetic trust anchor. Keys, SQLite/WAL/SHM files, state snapshots, and execution logs are not repository deliverables.

## Correction history and limitations

- The first migration run exposed a new effective-state integration reading a half-built 4B receipt inside its own transaction. The production integration was corrected to retain the fixed internal participant check; historical receipt validation remains strict. Populated migration tests then passed.
- The original versions 1–4 fixture accidentally copied a future model-prefixed UsageRecorded without its not-yet-supported model ledger. Migration correctly rejected this orphan. Those fixtures now use legitimate non-model legacy Usage; the populated versions 5–9 retain genuine model history. No assertion or migration guard was relaxed to accept the orphan.
- Simultaneous startup can legitimately return DATABASE_BUSY while another process installs WAL/migrates. The test records this bounded refusal, verifies one successful migration, and validates a fresh retry, rather than treating busy as partial success.
- Early Action crash cases exposed missing original runtime/Generation binding and an immutable-column update in the fixed Task participant. Both production defects were corrected before the final successful crash run.
- These tests validate Linux process termination, SQLite atomicity, and registered synthetic evidence. They do not establish production provider receipt semantics, billing correctness, endpoint authentication, Windows termination behavior, or external exactly-once execution.
